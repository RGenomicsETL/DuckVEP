# GRCh38 load path: bounded keyset feasibility

The load uses a dedicated DuckDB connection and a single explicit transaction (`src/duckvep_model.c`). A keyset page can use the committed source queries within that transaction, ordered by the model's unique, validated keys: `seq_region`; `transcript_index`; `(transcript_index, exon_cdna_start)`; `(transcript_index, mature_mirna_start)`; `(transcript_index, protein_position)`; and `(seq_region, feature_start, regulation_feature_index)`. The page cursor is the last decoded row's key. An exact byte budget must count variable-length columns as well as fixed-width columns and release all page chunks and the result before executing the next keyset query. A fixed row cap alone is insufficient: 16,384 transcript rows exceeded 32 MiB; halving the cap to 8,192 succeeded for that page.

The experimental implementation wrapped each input query in a key predicate and `ORDER BY ... LIMIT`, buffered a page of fetched chunks, retried oversized pages at half the row limit, and enforced 32 MiB of decoded data. This is **not an admissible production path** for the GRCh38 model: the source query performs an ordered scan for *each* page, instead of continuing an ordered scan. The large count over the ordered transcript query also remains in the exact-capacity path. The 8,192-row probe had not completed its load after 117.90 seconds (last timestamp minus `start` in `keyset-probe.trace`), compared with 3.553 seconds median on origin/main. At that point its high-water RSS was 4,378,120 KiB (4.18 GiB), below the exact-capacity load's 5.21 GiB, but it had **not** completed, indexed, or published a model. No complete after-load time or peak can be claimed. The probe loaded an immutable binary, SHA-256 `7021186c69c7b4fa97ac922a549735dc47236a392d1e4bc8d981df9d6df23dca`, built with the stage trace and a keyset prototype. A complete model over multiple pages and a mutation/snapshot concurrency test remain necessary for any future paging implementation.

The exact-capacity pre-count raises RSS by 178 MiB and median load time by 31% without paging, and adds a multi-gigabyte ordered result before native array allocation. It does not meet the no-regression criterion. A viable bounded loader needs an indexed or otherwise resumable ordered source that avoids repeated full sorting under the stable v1 C API; the stable v1 extension ABI does not expose the materialized result's random-access chunk APIs. Physical placement, temporary staging and a streaming execution strategy each require independent time, memory, correctness, and snapshot measurements before selection. Reverting the pre-count returns the public load path to origin/main behavior, at the cost of losing exact native reservations.
