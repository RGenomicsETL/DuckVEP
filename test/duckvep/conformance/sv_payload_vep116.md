# VEP 116 structural intervals and insertion payload

`rduckvep_prepare_sv_geometry()` projects a VCF allele into a nominal annotation span and separate breakpoint-confidence provenance. For symbolic VCF alleles, the affected start is POS+length(REF), the end is INFO/END, the outer/inner start are start+CIPOS[1/2], and the inner/outer end are end+CIEND[1/2]. The native `duckvep_annotate_sql` builder consumes the **nominal** event columns; confidence columns stay in the caller's event-index-keyed provenance table. VEP 116's JSON does not report inner/outer coordinates, so the executable comparison below tests only the asserted consequence invariance and nominal coordinates, not an oracle identity for CI bounds.

For a literal anchored insertion, inserted_sequence is ALT after REF and the event is passed as a small variant (no structural_type). VEP 116 reports that payload as `-/ATG`. For a symbolic `<INS>` with INFO/SEQ, the field is retained as `source_sequence`, not assigned to inserted_sequence: VEP 116's symbolic insertion consequences use the structural path and do not use INFO/SEQ as a literal allele. This difference is observable at chr21:13546123: the transcript ENST00000427446 is `feature_elongation&non_coding_transcript_variant` for `<INS>` and `splice_region_variant&non_coding_transcript_variant` for `G>GATG`.

Run `Rscript test/duckvep/conformance/sv_payload_vep116_differential.R` with the pinned Docker VEP 116 runner, GRCh38 chr21 cache, Ensembl 116 model, and GRCh38 FASTA. The script checks the FASTA anchor, 3 nominal VEP start/end pairs, 18-transcript nominal/CI consequence invariance in both engines, and the VEP-versus-DuckVEP symbolic and literal predicate above. It loads a private immutable extension copy and uses `FROM query(duckvep_annotate_sql(...))`; it writes no receipt. The paired-corpus exact-span SV, BND, repeat, regulatory, and motif gates remain separate conformance tests.
